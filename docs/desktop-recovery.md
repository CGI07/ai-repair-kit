# Codex Desktop recovery

This page describes the published AI Repair Kit 1.0.0rc3 rules and the compatibility checks in the local 1.0.0rc4 candidate.

Close Codex and ChatGPT completely, including background processes, CLI sessions, and IDE extensions. Start AI Repair Kit independently. Use **Diagnostics** to select the exact local Codex data folder and run a read-only check.

| Symptom | What the utility can do | Write support |
| --- | --- | --- |
| Projects still in SQLite but the Desktop registry is empty | Confirms the empty registry, surviving projects and accessible roots | Rebuilds only `local-projects` for reported Desktop build `26.911.7940.0` when every project has exactly one original legacy ID and valid ordered roots |
| Complete registry entries missing only createdAt or updatedAt after a custom migration | Reports cache entries with absent timestamp fields | On MSIX `26.903.8094.0`, fills only missing timestamps from exact, uniquely mapped SQLite project records. Existing IDs, names, roots, chat links and fields are preserved. Conflicting values, incomplete registries and journals are refused |
| Projects or old chat grouping missing and a trusted pre-incident snapshot exists | Corroborates project IDs, original roots, local host mapping, and exact historical thread IDs against current SQLite | Preview and merge only proven additions for reported Desktop build `26.1013.3656.0` |
| Empty local project registry and chat assignments after incomplete assignment migration | Corroborates the exact project and thread IDs against a known-good historical snapshot and the guarded state database | Cache-only repair on `26.1029.7803.0`. Supports a complete, lockable WAL and SHM pair |
| Empty or partial registry with exact original Desktop IDs | Counts missing registrations and detects shared roots, ambiguous IDs and missing evidence | Diagnosis only on MSIX `26.915.4065.0`. The registry-write rule is covered by synthetic lab tests |
| Empty registry with object-format cache links | Reports object-shaped cache assignments and compares recorded links | Diagnosis only on MSIX `26.924.2738.0`. The historical write rule is covered by synthetic lab tests |
| Projects and chats remain visible but recorded links differ across stores | Reports the SQLite and cache observations independently | No assignment rewrite based on a null SQLite link. MSIX `26.1103.4239.0` displayed chats using intact cache links |
| Work shows No projects and the account-scoped registry is empty or incomplete | Counts missing registrations and still-stored links. Compare a separate pre-incident cache with the active profile and SQLite | Local rc4 registry-only rule. The Windows x64 package restored both original projects and their existing chats after full registry loss in MSIX `26.1103.4239.0` and confirmed an app restart. Partial loss has synthetic coverage |
| NULL thread project link and one matching working directory | Reports exact-root candidates and leaves their membership unassigned | No path-based repair. A projectless chat may be intentional |
| Session file exists but history is missing or duplicated | Compares UUIDs in session filenames, name-index records and current thread metadata | No index rewrite, transcript import, or SQLite edits |
| Goal missing or inaccessible | Counts surviving `thread_goals` in the legacy state database and in `goals_1.sqlite` when present. Reports Goal rows without a matching thread when the thread DB can be checked | No Goal writes. Reopen the original thread to see whether Codex displays its Goal |

The published rc3 write rules are tied to the four builds listed above. The local rc4 candidate detects the current Windows package automatically. Every forward repair still requires the current user's registered Store x64 Codex package to match the version at preview, at apply and after backup. A missing or changed package blocks the write.

### Compatibility in the rc4 candidate

Diagnostics checks legacy registry shapes, string and object chat links, scope, project order, and migration state. It compares the cache and any explicitly selected pre-incident snapshot with available SQLite identities and ordered roots. The screen separates a read-only candidate from write eligibility. It reports candidate fields and project and chat counts, including excluded historical links. If a database schema is unavailable, independent cache, session and Goal checks continue where possible.

The timestamp-only repair can use a package version outside the published list if the active local profile and database match, the project key schema and original IDs are valid, the registry is complete, roots and host mapping agree, and existing timestamps do not conflict. The cache must use the legacy unqualified layout. The operation still changes only missing timestamps and refuses SQLite journals. Synthetic Windows tests verified the repair and a byte-for-byte rollback with a simulated new package number. Desktop visibility after this repair remains unverified.

Existing legacy empty-registry and historical-link rules retain their listed build and evidence constraints. The rc4 candidate adds an independent registry-only rule for the account-scoped layout observed in the offline lab. It requires an explicitly selected pre-incident cache, one matching active account, no inactive account records, the active local profile, exact SQLite project IDs and roots, and agreement on project order, mappings, assignments and migration state. It restores only absent registry entries and keeps their historical Desktop timestamps. SQLite timestamps can differ. An unknown scope, conflicting source, or a missing original chat link blocks this rule. The account-scoped chat link check remains read-only. With an intact registry and a separate pre-incident cache, it counts missing cache links whose explicit SQLite project IDs match the historical assignments. A NULL SQLite link leaves the old membership unconfirmed. An explicit projectless marker, changed current link, different scope, or conflicting ID prevents that evidence from authorizing a change.

Keep the pre-incident cache outside the active Codex data folder. On the reproduced failure, Desktop rotated its own companion backup to the empty registry while SQLite and both existing chat links survived. The local rule uses the normal process and file guards, including the sandbox service check. The utility does not manage that service. See the [VM verification record](desktop-vm-verification.md) for the current scope of runtime testing.

The [full issue #42739 review](issue-42739.md) distinguishes all 81 comments checked on November 8, 2026. It includes cases that remain unsupported, so a matching symptom is insufficient to authorize a repair.

The read-only check reports exact existing roots shared by multiple SQLite project records. It can read a profile-qualified local migration or mapping record when its path matches the selected folder. It does not open paths named in the cache and leaves conflicting local scopes unresolved. It also reports the recorded local migration state when the cache marks project migration complete and chat assignment migration incomplete. Valid pending IDs can be counted against a usable thread index without displaying any IDs. It also counts pending IDs that are explicitly marked projectless. That overlap does not establish original membership, so those markers are preserved. These observations can occur together, as reported for Desktop MSIX `26.1021.3705.0`. Keep the cache and database for review before re-adding a folder. [Public Windows report](https://github.com/openai/codex/issues/55869)

If the thread database is missing, locked, or unsupported, the scanner still checks the separate Goal store and inventories supported session filenames. It reports what survives and marks thread comparison unavailable. When Codex leaves both WAL and SHM beside `state_5.sqlite` or `goals_1.sqlite`, AI Repair Kit can include committed WAL changes in Windows diagnostics. This can show projects, thread links, rollout references and Goals that are absent from the main file alone. It must be able to guard all three files against changes. SQLite reconstructs the WAL index in memory. The reader also accepts a guarded zero-byte WAL left by a checkpoint for read-only diagnosis. A busy, incomplete or unsupported file set is skipped. Close Codex and its background processes before retrying, and keep the database and its journal files together. The result describes the committed data SQLite can read. [SQLite WAL documentation](https://sqlite.org/wal.html#use_of_wal_without_shared_memory) · [SQLite checkpoint modes](https://sqlite.org/c3ref/wal_checkpoint_v2.html)

## Check one thread

After a scan, choose **Check a specific thread or Goal** and enter the thread UUID or paste its `codex://threads/<thread-id>` link. If the configured SQLite location changed after the scan, run diagnostics again before checking the thread. Use an existing link or the Desktop **Copy chat deep link** command when the chat is accessible. AI Repair Kit checks presence in the state database and both Goal layouts without opening the link, reading the conversation or displaying the Goal text. A missing table, an unavailable database and an absent matching record are reported separately. When Goal records survive, the view shows each recognized status. When both stores contain a record, it reports whether the recorded IDs and statuses agree without displaying the IDs or assuming which store is current. On Windows, it keeps the state database guarded against changes while it reads the separate Goal store. [Codex Goal schema](https://github.com/openai/codex/blob/main/codex-rs/state/goals_migrations/0001_thread_goals.sql) It compares the recorded SQLite project with the Desktop cache assignment for that thread. A restored cache-only assignment can appear even when SQLite remains unassigned. Conflicting recorded IDs, missing mappings and explicit projectless markers are reported without printing project names or IDs. It also counts matching active and archived rollout filenames, including compressed and reverted variants. Plain and compressed copies of the same filename in one directory count once. The state DB reference is checked separately. It distinguishes a matching file, a missing referenced file even when older copies remain, and a filename that encodes a different thread ID. Unsupported paths are skipped. File presence does not verify transcript contents or what Desktop will display. [Codex thread schema](https://github.com/openai/codex/blob/main/codex-rs/state/migrations/0001_threads.sql) [Codex rollout filename parser](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/rollout_file_name.rs) [Desktop commands](https://learn.chatgpt.com/docs/app/commands)

### A chat opens with only part of its history

Check the exact thread first. AI Repair Kit can establish whether the state row and its referenced session file are present. For a thread recorded as paginated, it also checks whether the known `thread_history_1.sqlite` file is present, absent, or unavailable at the selected SQLite location. The app checks file metadata only. File presence establishes neither message coverage nor what Desktop displays. A missing file is an observation about the selected local profile. [Upstream history metadata](https://github.com/openai/codex/blob/main/codex-rs/state/src/model/thread_metadata.rs) [History database schema](https://github.com/openai/codex/blob/main/codex-rs/state/thread_history_migrations/0001_thread_history.sql)

Public reports describe several distinct failure points.

- After compaction, a reporter found user messages in replacement history while some displayed items were blank. Compaction records and other internal events do not map one-to-one to visible chat messages. [Compaction report](https://github.com/openai/codex/issues/41954)
- A Windows report described retained local events with missing indexed turns after an update. Another reported a persisted projection offset beyond the referenced continuation file. These are reported cases with different evidence. [Missing indexed turns](https://github.com/openai/codex/issues/43858) [Stale projection offset](https://github.com/openai/codex/issues/44594)
- A Windows report found completed replies in both the rollout and the history index despite incomplete display. The report leaves open what happened to transient, unfinished output. [Desktop rendering report](https://github.com/openai/codex/issues/59389)

The App Server can return metadata without turns, and paginated APIs can return only part of the history. Check cursor exhaustion, direction, and item detail level before comparing pages. The history index has separate turn, item, and projection tables. Counts from the rollout, history index, and rendered view can measure different things. Goal records are stored separately from chat items. An autonomous Goal can continue producing assistant or tool activity without a new user message. [App Server protocol](https://learn.chatgpt.com/docs/app-server) [Goal behavior](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)

A Desktop copy or screenshot shows what was captured from the UI at that moment. Compare the same thread and note the exact build, whether older pages had loaded, and whether the issue survives reopening. Keep original files intact and use a redacted summary or synthetic reproduction in an issue. AI Repair Kit does not compare message bodies, repair history projection state, or infer deletion from missing UI items.

### Archived chats and Goal records

The exact thread check shows the archive flag from SQLite separately from file presence. When the thread is marked archived, its referenced rollout is present in the archive, and the scan finds exactly one archived rollout and no active copy, look for that chat under **Settings > Archived chats** in Codex. If it is listed, use Codex's **Unarchive** action. AI Repair Kit reads metadata and filenames for this check. [Codex settings](https://learn.chatgpt.com/docs/app/settings#archived-chats) [Codex App Server archive behavior](https://learn.chatgpt.com/docs/app-server#archive-a-thread)

The documented Goal API creates or updates a Goal. Creating one from a previous objective can reset the usage history and does not provide a way to supply the missing record's original ID and accounting. Goal diagnosis remains read-only. [Codex App Server Goal API](https://learn.chatgpt.com/docs/app-server#manage-a-thread-goal)

## Preview and rollback

- Use **Preview project cache repair** for the empty-registry or missing-timestamp case. The rc4 candidate checks the installed MSIX automatically. The timestamp preview counts existing projects to update and fills only absent numeric `createdAt` and `updatedAt` values. All registry entries must match the complete uniquely mapped SQLite catalog, including their original IDs, names and ordered existing roots. Existing timestamps must agree with SQLite and saved chat assignments must reference recognized local projects. No project or chat membership is created by this rule.
- The empty-registry repair retains all other JSON fields. On diagnostic-only builds, keep the original cache and any trusted historical snapshots for review.
- Use **Preview recovery from a historical snapshot** for the second case. Select an intact Desktop cache from the same profile, saved before the incident as `.codex-global-state.json`, `.codex-global-state.json.bak`, or a `.codex-global-state.json.tmp-*` file. The temporary suffix must contain 1–128 ASCII letters, digits, hyphens or underscores. A temporary file can be incomplete or newer than the incident, so its filename does not establish trust or precedence. If you already have a verified cache copy under another name, make a separate copy with a recognized name. The picker and the recovery engine restrict the filenames they accept. The rule preserves current projects, current assignments, explicit projectless markers, relative order of current projects, and unrelated settings. It skips historical links to missing threads, conflicting assignments, or uncorroborated projects. It also skips a project when either the current or historical local host mapping uses multiple Desktop IDs for the same SQLite project. The preview counts the excluded links. Absent or null settings stay as they were when the repair does not need to populate them. It uses neither CWD inference nor newly generated project IDs. Keep the snapshot available through approval and repair. If it changes or disappears after the preview, the repair stops. Windows denies writes and renames on the selected snapshot while repair is in progress.
- Review the proposed target and the counts of additions and exclusions. Approval saves a verified copy of the complete original Desktop cache in the per-user `recovery-backups/desktop` folder before replacing the file. The backup may contain private local settings. Keep it local. The utility leaves SQLite, its sidecars, session files, Goal stores, migration flags, and Codex's own backup files as they were.
- A Windows process snapshot checks recognized Codex and ChatGPT executable names before backup and again before replacement. If a matching process appears, the app stops without terminating it. The app also compares the target file again before replacing it. If the profile configuration redirects SQLite after the scan or changes after the preview, the app stops and requires a fresh scan. The Windows replacement keeps a same-directory displaced copy until verification. If Windows holds a temporary recovery file after verification, it may remain in the profile. The verified result and its backup are still usable. On failure it attempts rollback when the current bytes still match the tool's output. If another program replaces the cache during rollback, AI Repair Kit retains the competing bytes in the same-directory `.ark-*.rejected` file and reports that rollback could not be verified. If rollback cannot be verified, keep the backup and any `.ark-*` recovery files and leave Codex closed while inspecting them.
- With the intended profile selected, open **Backups**, refresh, select the Desktop cache backup and choose **Preview rollback**. The list shows up to 100 verified Desktop backups for that profile, newest first by file modification time. The preview shows the selected backup ID, byte count and checksum. The app verifies the same backup contents and exact current cache again after approval. It saves and verifies the pre-rollback cache so the rollback itself can be reversed. The newly created backup is selected automatically. A later Codex write, a changed backup or a replaced profile directory after preview blocks replacement. Desktop can reserialize the cache after reopening even when the JSON values are unchanged. The exact-byte rollback then stops. Complete an immediate rollback before reopening Codex when you need to reverse an untested change. New backups also record a digest bound to the original profile directory identity. Older rc2 backups remain readable and depend on their path and exact content hashes.
- If a replacement is interrupted and the cache file is missing, **Preview rollback** is available only when a same-profile verified backup matches the displaced original created by that specific operation. The app moves the verified original back without overwriting a file that appears in the meantime. Older backups without the matching displaced file still require manual inspection. [Windows replacement behavior](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)
- After success, reopen Codex, verify that the projects remain after restart, and open an old chat in its project. Confirm the Goal in the original thread. File verification confirms the replacement, while visibility and session behavior require checking the Desktop app.

The scanner skips locked files, rollback journals, unsupported formats, nonlocal roots, links, and bounded scans that cannot finish safely. A guarded state database with WAL and SHM is available for diagnostics. A complete, guarded pair with a valid WAL header can also provide evidence for the `26.1029.7803.0` historical rule. The account-scoped registry-only rule can also use a verified complete WAL and SHM pair. Other cache rules require a journal-free state database. Existing verified cache backups can still be reviewed. Preserve known-good backups. If Recents is filtered, clear the project or host filter in Codex and try Resume. If the source files, canonical SQLite records or exact historical associations are gone, the tool cannot reconstruct them.

## Rollback after Desktop rewrites JSON

The backup contains the exact original bytes and the SHA-256 of the approved output. A mismatch after Desktop opens can reflect formatting, a new setting, or a real edit. The current backup cannot distinguish these cases on its own. AI Repair Kit keeps the exact-byte rollback guard.

A later format-aware check would need verifiable evidence of the complete approved document. It would compare every key, value and JSON type, reject duplicate keys and unsupported numbers, and still recheck the exact current file hash at approval and replacement. It would also keep a verified copy of the current file before changing it. Matching project counts or inspecting a few fields cannot authorize rollback.

## Recheck after an update

Before an update, fully close Codex and retain a local copy of a known-good cache separately from the active profile. Keep a consistent copy of the state database with any existing journal companions if you need a comparison. Preserve the last verified copy when newer evidence is incomplete. Keep these copies private because the cache may contain other settings. After the update, compare the original project identities and exact link evidence in the intended account and profile, and test that an old chat opens under its project after a normal restart. If the app clears the cache again, retain the backup and collect the version and redacted support report. This candidate provides an explicit local review flow and does not schedule background backups or repeat writes.
