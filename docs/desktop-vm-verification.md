# Isolated Codex Desktop verification on Windows

Use this procedure to distinguish a file-level repair from restored visibility in Codex Desktop. Run Codex Desktop only inside the disposable Windows guest. Never point a guest or a host test at a real Codex profile, use a real account, or export the guest profile.

## Prepare the lab

1. Use a supported, approved hypervisor. On Windows Home, Microsoft's Hyper-V role is unavailable. If Oracle VirtualBox is approved, obtain the base package from Oracle and verify its published SHA-256 and Authenticode signer. The Windows installer supports selecting only `VBoxApplication`. Leave USB, host-only and bridged network drivers, and the Extension Pack out of this lab. Stop if further host changes are required.
2. Use a new Windows 11 x64 guest with UEFI Secure Boot, virtual TPM 2.0, and a dynamically allocated virtual disk of at least 64 GB. An initial allocation of 4 vCPUs and 8 GiB RAM is suitable if the host has resources available. Use a Microsoft installation ISO and an eligible evaluation or separately licensed Windows copy. Stop if setup requires a Microsoft identity that cannot be supplied as a separate test identity. Never use the host identity, recovery media, or physical disk. An offline first boot with a local account does not activate an evaluation. If Windows shows a license expiration notice or reports notification status, record it. Continue approved offline checks while the guest runs, and report any test interrupted by the evaluation shutdown or requiring activation separately. Connecting the guest requires separate approval and verified isolation. [Microsoft evaluation guidance](https://www.microsoft.com/en-us/evalcenter/download-windows-11-enterprise)
3. Before the first boot, turn off clipboard sharing and file transfers, drag and drop, shared folders, USB/device passthrough, and remote display. Leave Guest Additions out. Check that the VM has only its new virtual disk and the intended optical media. Configure networking only in the guest VM settings. Prefer offline installation media. If online access is necessary, use a separately approved path that blocks access to the host and LAN. VirtualBox NAT by itself does not prove that separation. Disconnect every virtual NIC for recovery tests. Detach the Windows install media after setup.
4. Deliver the built AI Repair Kit folder and synthetic fixture code via a read-only virtual optical image prepared from an explicit file list. Never attach the repository root, a host partition, a live folder, or a profile. Compare the transfer archive SHA-256 inside the guest before extracting it. Detach the transfer media after copying.
5. Install the Windows desktop app from the official OpenAI-documented distribution inside the guest. OpenAI also documents the latest Store-signed offline x64 MSIX. Verify the signature and record the version before installation. Check any offline license and dependencies in the official instructions. Record its package version, About build, and acquisition route. If separate authentication is needed, stop before signing in and record which unauthenticated checks are possible. Use an approved test account only. A current Store package establishes coverage for that build alone. A specific historical build requires a verifiable official package before claiming coverage.

## Verify isolation before any profile test

- Save the VM configuration for the record using `VBoxManage showvminfo <vm> --machinereadable`. Verify that clipboard and drag and drop are disabled, the shared-folder lists are empty, physical disks and USB controllers are absent, and all NICs are disabled during the test. Check the intended VDI and any temporary optical media paths. Keep this evidence local. For the standard eight-adapter VirtualBox 7.2 lab, pipe the command output to the read-only check below. Use the recorded VM UUID. The check expects the lab's disabled sharing and peripheral settings and never opens paths from the output.

  ```powershell
  $settings = & $vbox showvminfo $vmId --machinereadable
  if ($LASTEXITCODE -ne 0) { throw 'Could not read the VM settings' }
  $settings | .\.venv\Scripts\python.exe scripts/check_vbox_lab.py $vmId
  if ($LASTEXITCODE -ne 0) { throw 'The VM settings need review' }
  ```

  Check the VBoxManage exit status and the verifier result. Independently confirm the expected VDI and optical images, then continue with the guest checks.
- From the guest, confirm that Explorer shows only guest storage after removing optical media. Check `Get-SmbMapping` and `Get-PSDrive -PSProvider FileSystem` for network or redirected drives. Check `Get-NetRoute -AddressFamily IPv4` and `Get-NetRoute -AddressFamily IPv6` for external routes. In both directions use a generated harmless marker to confirm clipboard content and a dummy file cannot cross. Do not test with host private paths or clipboard contents.
- Create a powered-off clean snapshot after installation and verify it is listed. Create a second baseline snapshot after the guest can reopen its synthetic project, chat, and Goal. Verify snapshot restoration once before using it for destructive fault injection.

In the guest, the packaged AI Repair Kit reported a surviving project, incomplete assignment migration, a pending ID absent from SQLite, a missing session reference, and records in both Goal stores. The cache and two SQLite files kept the same SHA-256 values. On the same synthetic profile, the application previewed and applied the empty-registry repair, verified the backup, and restored the original cache through the Backups screen. ### Project-link rollback on a disposable profile

The [project-link lab verifier](../scripts/verify_codex_link_lab.py) generates two projects, two persisted threads, and a paused Goal using the bundled App Server. It takes no profile path. It checks the supplied VirtualBox guest UUID, the local ArkLab account, the installed package and App Server versions, and the absence of external addresses, default routes, and SMB mappings. Check the hypervisor's isolation and snapshot separately before running it.

Build the console verifier on the development host and deliver the resulting EXE alone through verified read-only optical media. Use the existing project virtual environment and the PyInstaller packaging dependency.

```powershell
$labOutput = '.test-work/native-link-lab'
.\.venv\Scripts\python.exe -m PyInstaller --onefile --console --noupx --name Ark-Link-Lab `
    --distpath $labOutput/dist --workpath $labOutput/build --specpath $labOutput `
    scripts/verify_codex_link_lab.py
Get-FileHash -LiteralPath "$labOutput/dist/Ark-Link-Lab.exe"
```

In the guest, confirm the EXE hash and use `Ark-Link-Lab.exe --guest-uuid <recorded-vm-uuid> --run-synthetic-test`. The test creates a fresh fixture under the disposable guest profile and retains its backup and post-mutation copy for inspection. This lab program performs writes to that fixture. The product EXE does not expose this mutation.

The Windows 11 guest passed the verifier with MSIX `26.1029.7803.0` and App Server `0.166.0-alpha.6`. It verified a stopped-profile backup byte for byte before mutation. App Server refused an unknown project, preserved the target assignment after a repeated request and a restart, and reopened the target as unassigned after an API rollback. The independent file rollback restored the verified backup at the fixture's original path. Reopening confirmed the unassigned target, the sibling's original assignment, and the unchanged Goal record. Both rollout files retained their original hashes. The guest PowerShell execution policy rejected an initial script-based verifier. The console build ran without a policy change.

The experimental API accepts a project ID but has no field for the expected previous assignment. Its transaction validates the project and sets the link, so a preflight read plus a later request cannot rule out overwriting an intervening edit. The lab had one owner and a stopped-profile backup. A user-facing mutation still needs an enforced stale-state guard, approval-bound backup and rollback, and an observed Desktop result. [App Server thread schema](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs) [Project persistence](https://github.com/openai/codex/blob/main/codex-rs/state/src/runtime/projects.rs)

The optional `--experimental-sqlite` lab probe attempted a direct conditional transaction on the disposable profile. SQLite refused a competing writer and preserved the later assignment when the preview was stale, but opening a rejected write transaction still changed SQLite state file bytes. The eligible write then stopped at an existing Codex trigger on `threads`. This is a failed direct-write verification. The product leaves these writes unavailable. [SQLite transaction semantics](https://sqlite.org/lang_transaction.html)

## Record file and GUI results separately

1. Create a new project and synthetic chat in the guest using the app's normal entry points. If supported, create a test Goal there. Confirm all three appear after an ordinary restart. When a feature requires a live service, record that requirement and whether offline restart is testable. Record counts and statuses only. Stop if the normal baseline cannot be reproduced. A fabricated database is useful for repair-engine tests and cannot establish normal app visibility.
2. Shut down the guest Codex app. On a snapshot branch inject one confirmed fault at a time using the guest's test profile only. Compare with the original baseline. Reopen Codex to observe the symptom, then shut it down before running a repair. For the migration case, claim an update reproduction only if the official source and destination builds are available and the actual update produced it. An injected post-update state can be recorded separately.
3. Run AI Repair Kit diagnosis, review the preview, confirm the approved target, and verify its backup and post-write result. Record refused candidates, SHA-256 evidence for files expected to remain unchanged, and any manual or automatic rollback result. Reopen Codex and record what actually reappears. If any issue cannot be reproduced or the app cannot reopen offline, mark the corresponding GUI result unverified. Revert the branch before injecting a different fault.

| Case | File-level result to record | GUI result to record |
| --- | --- | --- |
| Empty Desktop registry | Only the supported registry field changes, verified backup and rollback | Existing projects reappear after restart |
| Exact historical cache links | Only corroborated associations are added, ambiguous threads stay excluded | Expected old chats reopen from the correct projects |
| SQLite/cache disagreement or missing rollout | Read-only result reports the mismatch or absent reference | Observe the symptom and whether a separate supported action changes it |
| Goal differs across stores | Read-only result distinguishes presence, identity and known statuses | Record presence for the same reopened synthetic thread, including whether the project repair alone changes it |
| Interrupted cache replacement | Verified displaced original can be restored if the target is absent | Reopen the app and compare with the pre-interruption view |
