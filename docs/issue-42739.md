# Codex issue #42739 evidence review

Reviewed on November 7, 2026. The review covers the issue body and all 79 comments returned by GitHub at that time. Comments include follow-ups from the same installations, corrections, possible duplicates and mixed procedures. They are not 79 independent incidents. Personal paths, user names, support identifiers, project names and conversation contents have been omitted.

The issue remains open. A single action cannot reliably resolve every report. Local cache repair can address surviving metadata under a matching rule. It cannot establish a cloud account fix, override feature gates, recover absent history, resolve conflicting intent, or prevent a later Desktop write from undoing a repair.

## Cases and current actions

| Evidence pattern | Action and limits |
| --- | --- |
| Empty cache, complete unique legacy mapping, MSIX 26.911.7940.0 | Existing project-only repair. Original IDs and unrelated settings are preserved. |
| Existing projects missing only numeric timestamps, MSIX 26.903.8094.0 | Fill only absent createdAt/updatedAt from the matching SQLite records. Require the complete registry and unique mapping, existing roots, matching names and IDs, and consistent existing timestamps. The report attributes the initial malformed entries to a custom migration. |
| Exact historical snapshot, MSIX 26.1013.3656.0 or the documented 26.1029.7803.0 migration case | Existing exact-link cache repair. Recognized .tmp-* snapshots are now accepted alongside the normal cache and .bak. A temporary filename does not establish provenance. The user selects a trusted pre-incident copy and the content is validated. |
| Pending and projectless IDs overlap | Report only the unique count when both lists have recognized IDs. Preserve explicit projectless choices and require separate evidence of membership. |
| Directory match, Git origin match, duplicated roots, conflicting snapshots | No automatic membership inference or deduplication. A newer file alone does not resolve a conflict. Preserve the evidence. |
| Non-null canonical assignments but empty renderer catalog | The public reports establish that a database-only repair can fail to change Desktop. Use only a rule with matching cache representation and evidence. |
| Assignment objects, profile-qualified migration host keys or account-scoped renderer state | These formats require separate validation. Do not coerce them to the legacy string/local-host layout or copy another account's state. |
| Wrong CODEX_HOME, unhonored launch overrides, cloud or remote project | Verify the selected profile and the intended account/workspace through supported app settings. The current process environment does not prove which profile an already-running app uses. The utility does not change system environment or cloud data. |
| Repair disappears on restart | Preserve the verified backup and record the post-restart failure. Repeated cache writes cannot establish a durable fix. Desktop reconciliation remains an upstream issue. |
| Missing or damaged source metadata, unknown schema, inaccessible roots, incomplete journals | Stop writes and explain what could not be verified. File presence and quick_check alone do not establish complete conversation history. |

The new timestamp implementation and temporary-snapshot extension are tested with synthetic fixtures, including stale evidence, denied approval, backup failure and rollback. The project's isolated Desktop window still cannot be used under the current offline restriction, so an independent Desktop visibility result for these additions is pending. Success described in a public comment is distinct from verification of this implementation.

## Verification after a repair

Keep the original project identities, metadata and verified backup. Reopen the affected app yourself and check that project containers persist after a normal restart and that an older chat opens in its original project. Inspect the original Goal separately. Confirming JSON bytes is only the file-level result. If the app rewrites the cache or still hides the project, keep the result unverified and report the build and synthetic reproduction without private profile files.
